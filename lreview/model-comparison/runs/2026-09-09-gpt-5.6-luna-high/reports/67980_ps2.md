# 67980 ps2 — LU-20582 llite: fix statahead SFNAME pattern detection

- **Change:** https://review.whamcloud.com/c/fs/lustre-release/+/67980 (patchset 2, `f3b4f4d37635`)
- **Review:** 2 finding(s)
- **Run:** gpt-5.6-luna, 6.1M tokens, 9m45s

## Overall assessment

Problematic, see inline comments. The shared FNAME cache can lose one process's detection state when another process with a colliding PID hashes a malformed name into the same slot.

## Findings

### 1. `lustre/llite/statahead.c` (line 2329)

(defect) Can the invalid-name/parse-error path avoid clearing a slot owned by another PID? `sa_pattern_sfname_detect()` selects `current->pid % LSA_MAX_SEE_ENT`, but `sa_sfi_detect()` jumps to `reset:` before it checks `*pid != current->pid`. If PID A has a valid entry and PID B hashes to the same slot, a stat of `README` (or an unparseable numeric suffix) by B zeroes A's `sse_pid` and match state. A's next consecutive stat starts over, so unrelated malformed-name stats can prevent the shared FNAME detector from ever reaching `match_hit`.

### 2. `lustre/llite/lproc_llite.c` (line 1106)

(minor) This adds the user-visible `llite.*.enable_statahead_sfname` tunable, but there is no matching `Documentation/man4` page in the patch. Could the parameter's default and its coupling to `enable_statahead_fname` be documented?
