## Findings

### 1. `lustre/llite/vvp_io.c` (line 1579)

(defect) Is clearing PageUptodate on its own enough to force the next read back through ll_readpage()? cp_defer_uptodate is left set on these pages.

A readahead page whose read succeeded is deliberately left !PageUptodate with cp_defer_uptodate == 1 in vvp_page_complete_read(), and nothing clears that flag afterwards. lov_ec_read_stripe_pages() classifies purely on PageUptodate(), so such a page on an LSS_READ_ERR stripe becomes EC_DPG_ERROR and lands on ec_page_list; cl_page_find() returns the pre-existing cl_page, so the flag survives reconstruction and this clear.

The next read then short-circuits in ll_io_read_page():

    uptodate = page->cp_defer_uptodate;
    if (uptodate) {
        SetPageUptodate(page->cp_vmpage);
        cl_page_disown(env, io, page);
    }

and the fast-read path in ll_readpage() (io == NULL) re-sets it without entering the io stack at all. Either way the reconstructed contents are served again with no RPC and no fresh DLM lock, which is the coherency the clear is meant to restore.

sanity-ec test_74a deactivates the OST while readers are running, so pages sitting in the readahead window in exactly that state are the common case rather than a corner. Should cp_defer_uptodate be cleared alongside PageUptodate here?
