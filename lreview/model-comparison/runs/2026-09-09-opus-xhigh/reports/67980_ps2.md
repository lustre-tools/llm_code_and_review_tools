# 67980 ps2 — LU-20582 llite: fix statahead SFNAME pattern detection

- **Change:** https://review.whamcloud.com/c/fs/lustre-release/+/67980 (patchset 2, `f3b4f4d37635`)
- **Review:** 5 finding(s), severity **medium**
- **Run:** opus, 4.9M tokens, $6.31, 16m57s

## Overall assessment

Some concerns, see inline comments. Two of them are in the new shared-fname detection path and defeat the detection this patch is trying to make reliable.

## Findings

### 1. `/COMMIT_MSG` (line 37)

(minor) The body only describes the new shared-fname cache, but the diff also reworks the non-shared detectors.

sa_pattern_list_detect() and sa_pattern_fname_detect() change from bool to enum sa_pattern_detect_rc, a negative return from either now aborts the whole sa_pattern_detect() chain instead of falling through to the next detector, and sa_pattern_fname_detect() gained an ll_sa_reset_locked() call on the !lli_sa_enabled path that the old code did not have. test_123k also switches from enable_statahead_fname to the new knob.

Could the body say why each of those is needed, so a later reader doesn't have to guess which of them are intentional?

### 2. `/COMMIT_MSG` (line 39)

(defect) This points at the commit that added the three validation checks, not at the one that bypasses them.

In e10bf68d7c, sa_pattern_fname_detect() had no multi-pid handling at all: it enforced the trailing-digit test, the num == index + 1 consecutiveness test and lli_sa_match_count > LSA_FN_MATCH_HIT.

The shortcut this patch removes -- `if (lli->lli_sa_pattern & LSA_PATTERN_FN_SHARED) return true;` and the lli_stat_pid != current->pid block that sets FN_SHARED and returns a match -- came in later, so should this read:

    Fixes: 629b0534e141 ("LU-14361 statahead: add support for mdtest shared dir workload")

### 3. `lustre/llite/llite_internal.h` (line 132)

(typo) SEE looks like it should be SSE, to match struct ll_sa_sfname_entry and its sse_ field prefix.

### 4. `lustre/llite/statahead.c` (line 2330)

(defect) reset: does `*pid = 0` plus the memset, and both goto reset paths run before the `*pid != current->pid` test further down. So a task clears the slot even when the slot belongs to a different task.

With the shared cache installed, sa_pattern_sfname_detect() reaches here for every name, not only numeric ones -- its own !isdigit() precheck is skipped once lli_sa_sfname_cache is non-NULL. One stat of $dir/README by a task with a colliding pid % LSA_MAX_SEE_ENT therefore wipes another task's accumulated sfi_match_count and sfi_last, and that task has to start counting again.

The kstrtol() failure below has the same effect, and base 0 rejects zero-padded names containing 8 or 9 (f.000009), which is a naming style start_statahead_thread() explicitly supports via sai_fname_zeroed_len.

Should the ownership test move above the two goto reset paths, so a foreign entry is left untouched?

### 5. `lustre/llite/statahead.c` (line 2393)

(defect) The `!lli->lli_sa_sfname_cache &&` qualifier makes this precheck one-shot. The cache is only memset by ll_sax_put()/ll_sa_reset_locked() and only freed in ll_inode_destroy_callback(), so after the first shared round it is never NULL again and the digit test is skipped on every later pass.

From then on a second pid stat'ing any name falls through to `lli->lli_sa_pattern |= LSA_PATTERN_FN_SHARED` below. sa_pattern_fname_detect() bails out on `pattern & LSA_PATTERN_FN_SHARED` for the rest of the round, so a single stat($dir/README) by an unrelated process demotes a single-process mdtest-style scan out of the FNAME detector and drops the lli_sa_fname progress it had built up (sa_alloc_sfname_cache() only migrates that state when it allocates the cache).

Dropping the `!lli->lli_sa_sfname_cache &&` part keeps the guard working on every pass.
