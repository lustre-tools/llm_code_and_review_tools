## Findings

### 1. `lustre/ptlrpc/gss/sec_gssiam_srv.c` (line 407)

(defect) Should the cookie be swabbed at all? Connection handles are opaque 8-byte cookies that round-trip byte-for-byte, so nothing in ptlrpc swabs them: lustre_swab_ptlrpc_body() deliberately starts at pb_type and never touches pb_handle, and lustre_swab_ldlm_request() spells the same rule out with "lock_handle[] opaque". On the client side ptlrpc_connect_interpret() copies the cookie raw out of the reply into imp_remote_handle and ptl_send_rpc()->lustre_msg_set_handle() writes it back raw.

So for the same request the core path resolves the un-swabbed value:

    req->rq_export = class_conn2export(lustre_msg_get_handle(req->rq_reqmsg));

while this one resolves a byte-reversed one.

For an opposite-endian client - the case this change is about - class_conn2export() then misses, h_exp stays NULL, and gssiam_handle_init() falls back to req->rq_export, which is still NULL this early in sptlrpc_svc_unwrap_request(). tgt_gssiam_verify() takes its no-export branch and gssiam_ctx_install_nodemap() is skipped, so the refreshed identity never gets bound to the live export.

The swab came over from the old req_capsule_req_need_swab() branch, but since the point of the change is endianness correctness it looks like it should be dropped.
