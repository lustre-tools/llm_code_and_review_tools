## Findings

### 1. `lustre/llite/statahead.c` (line 2456)

(defect) Could an expired single-process owner be released before this PID check? With enable_statahead_fname=1 and enable_statahead_sfname=0, process A can leave a partial match and exit before a worker starts. Every later process B returns here, and the shared detector returns -EACCES. The one-second expiry in sa_sfi_detect() is never reached. lli_sa_enabled stays set, so ll_statahead_enter() also cannot restart prediction. A subsequent sequential scan therefore never starts FNAME statahead on this cached directory, even after waiting past the expiry.

### 2. `lustre/llite/statahead.c` (line 2330)

(defect) Should the slot ownership/expiry check run before either filename-parse failure can reset the entry? Once the shared cache exists, a task with a colliding PID reaches sa_sfi_detect() even for a nonnumeric name. For example, PID 100 can own slot 0 with a valid partial sequence, then PID 105 stats README: this reset clears PID 100 and its match count before checking ownership. Repeating those accesses prevents PID 100 from matching despite consecutive stats within the one-second validity window. Invalid numeric suffixes take the same reset path.

### 3. `/COMMIT_MSG` (line 39)

(minor) Could the Fixes trailer point to 629b0534e141 ("LU-14361 statahead: add support for mdtest shared dir workload")? That change introduced the different-PID early success before numeric sequence and match-count validation. e10bf68d7c introduced the original filename detector, which still applied those checks and had no shared-process bypass.
